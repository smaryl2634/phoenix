# 不死鸟 Phoenix 三场景配置指南

不死鸟能不能真的按任务复杂度自动切换模型，取决于 `config/tiers.json` 怎么填。先判断
你属于哪种情况，再照对应步骤配置。

## 你是哪种情况？

- 有一个"中转站"账号，一个 API Key 能调很多不同模型 → 看下面**场景A**
- 只有一个模型能用（没有中转站，也没有单独买其他模型的Key）→ 看**场景B**
- 好几个模型分别买了独立的 Key（比如 DeepSeek 一个Key、Kimi 一个Key）→ 看**场景C**

## 场景A：中转站用户

先在 Hermes 自己的配置里（HERMES_HOME 目录下的 `config.yaml`，macOS/Linux 默认 `~/.hermes/config.yaml`，Windows 默认 `%LOCALAPPDATA%\hermes\config.yaml`，可用 `HERMES_HOME` 环境变量覆盖）加你的中转站信息：

```yaml
model:
  provider: "custom"
  base_url: "https://你的中转站域名/v1"
  key_env: "MY_RELAY_KEY"
```

**重要（2026-07-30 真机验证更正）**：下面这段曾经写过"中转站对不同模型家族用不同接口
URL 时，配多条 `custom_providers` + `tiers.json` 里填 `custom:<name>/模型名` 就能让
phoenix_v7 按档位自动切换 base_url"——**这个写法真机测试不生效，而且不是格式写错，是
Hermes 当前架构做不到，phoenix_v7 补不了这个缺口**。以下是结论和真正能用的配置方式。

### 为什么做不到

phoenix_v7 的自动路由是通过 Hermes 的 `llm_request` middleware 挂进去的
（`__init__.py::_route`）：它能做的只是把已经建好的请求里 `model` 这个字段的值换掉，
换完之后仍然通过**这个会话建立时就已经固定好的** HTTP client 发出去——那个 client 绑定
的 base_url / api_key 在会话开始时就定死了，`llm_request` middleware 拿不到 agent
实例，没有任何钩子能在单次请求里把 client 重新指向另一个 base_url。也就是说 tiers.json
里填的值不管是什么格式，phoenix_v7 都只能在**同一个 base_url** 内切换模型名字符串，
换不了接口地址。

`custom:<name>/模型名` 这种写法本身在 Hermes 源码里确实存在解析逻辑
（`hermes_cli/model_switch.py::parse_model_input`），但它只服务于交互式聊天里手打
`/model custom:<name>:模型名`（**是冒号分隔，不是斜杠**）这一条路径，而且只有真正执行
了这次切换，才会重新解析 base_url / api_key / client。2026-07-30 用真实的假中转站配置
（两条 `custom_providers`，两个不同 base_url）实测验证过：

- `hermes chat -m "custom:relay-gpt/gpt-fake" --verbose` → `--verbose` 日志显示
  client 的 `base_url` 仍然停在默认那条 provider 上，`model` 字段被原样塞进了整个
  `"custom:relay-gpt/gpt-fake"` 字符串（没有被拆解、没有触发任何 provider 切换）。
- `hermes chat --provider "custom:relay-gpt" -m "gpt-fake" --verbose` → 直接报错
  `Unknown provider 'custom:relay-gpt'`。
- `hermes chat --provider "relay-gpt" -m "gpt-fake" --verbose` → 同样报错
  `Unknown provider 'relay-gpt'`。

`-m` / `--provider` 这两个命令行参数走的是另一条更早、更简单的校验路径，根本不认
`custom_providers` 里配置的具名条目，跟 phoenix_v7 走的 middleware 路径也完全无关。
不管文档怎么改写法，CLI 层面和 middleware 层面都没有一条真正跑通的路。

### 真正能用的配置方式

**情况一：中转站其实是同一个 base_url**（多数中转站是这样，不同模型家族只是模型名
前缀不同，接口地址是一个）——那就不需要配多条 `custom_providers`，`tiers.json` 里直接
填**裸模型名字符串**（不带任何 `custom:` 前缀），因为 phoenix_v7 只是覆写当前已经连上
的请求的 `model` 字段：

```json
{
  "enabled": true,
  "tiers": {
    "l2_deep": "claude-opus-4.8",
    "l3_critical": "gpt-5.5"
  }
}
```

配置前务必先确认：中转站的这个 base_url 是否真的能吃你想切的所有模型家族的模型名——
不确定就先跟中转站客服/文档核实一次，别直接猜。

**情况二：中转站真的对不同模型家族用不同 base_url**——phoenix_v7 目前做不到跨
base_url 自动路由，只能二选一：

1. 挑一个模型家族作为"自动挡"档位（`model.base_url` 配那个家族的地址），tiers.json
   按情况一填裸模型名；另一个家族只能手动切，在交互式聊天里输入
   `/model custom:另一个家族的name:模型名`（冒号分隔），phoenix_v7 不会碰这次手动切换
   之后的模型选择。
2. 或者干脆开两个独立的 hermes 会话/配置目录，一个绑一个 base_url，不指望自动路由跨
   家族工作。

`custom_providers` 多条记录本身没有错，只是它的作用是"给交互式 `/model` 命令提供可选
项"，不是"喂给 tiers.json 让 phoenix_v7 自动切"。

## 场景B：单模型用户

不用改 `tiers.json`，保持原样（空的 `{}`，或者 `"enabled": false`）就行。不死鸟依然会
判断每条消息该归哪一档，你能在日志里看到分类结果，只是不会真的切模型——因为你只有
一个模型，切了也没地方切。这不是没做完，是正常状态。

## 场景C：多模型分Key用户

先确认每个模型在 Hermes 自己的配置里都单独配好了 Key（DeepSeek/Kimi/智谱GLM等都是
Hermes 原生支持的，不用不死鸟插手）：

```bash
hermes model list   # 看看目前能用哪些
```

然后在 `tiers.json` 里按档位填对应的 `provider/model` 字符串：

```json
{
  "enabled": true,
  "tiers": {
    "l0_fast": "deepseek/deepseek-chat",
    "l2_deep": "kimi-coding/kimi-k2",
    "l3_critical": "anthropic/claude-opus-4.8"
  }
}
```

档位没提到的（比如上面例子里的 `l1_daily`）会自动落回 Hermes 当前设置的默认模型。

## 验证是否真的生效

```bash
hermes chat -q "你好" --verbose
hermes chat -q "帮我设计一个分布式系统的一致性方案" --verbose
```

第二句应该命中 `l2_deep` 或更高档位。用 `hermes plugins list` 确认插件是 `enabled`
状态；两条消息如果配置了不同模型，`--verbose` 输出或日志里应该能看到实际调用的
`model` 字段不一样。

## 随时开关

```bash
hermes phoenix-router off   # 关闭自动切换，只保留档位判断
hermes phoenix-router on    # 重新开启
```

不会丢失你已经填好的 `tiers.json` 配置，只是切换要不要真的生效。

## 欠费两级兜底：本地优先，云端兜底

如果你希望"云端模型欠费/额度耗尽时自动降级，而不是直接报错"，配的不是 `tiers.json`，
是 **Hermes 自己的** HERMES_HOME 目录下 `config.yaml`——根级的 `fallback_model` 字段。这不是
不死鸟的功能，是 Hermes 原生就有的能力（遇到 402/429/503 等故障会自动重建 client
换一套 provider/model 重试），不死鸟只是不会跟它打架。

```yaml
fallback_model:
  - provider: custom
    model: 你本地跑的模型名
    base_url: http://127.0.0.1:你的本地服务端口/v1
  - provider: 你的云端账号provider名
    model: 你账号下最便宜/免费的模型
```

几点说明：

- **第一条建议填本地模型**（Osaurus/Ollama/LM Studio 等，任何暴露标准 OpenAI 兼容
  `/v1/chat/completions` 接口的本地服务都行）。这个模型不需要多聪明——它唯一的职责是
  欠费时还能应一声、告诉你"该充值了"，不是要顶替云端主力模型干活，选个能跑起来的小
  模型就够了。
- **第二条填你自己账号下的便宜/免费云端模型**当第二级兜底（万一本地服务没开）。具体
  填什么完全取决于你自己的账号和预算，不死鸟不内置任何默认值。
- 本地服务通常不需要认证，`provider: custom` 且不填 `api_key`/`key_env` 时，Hermes
  会自动当作免密本地服务处理。
- 配置生效后，`hermes chat` 启动时会打印一行 `🔄 Fallback chain (...)`，能看到这行
  说明 Hermes 已经识别到你配的链。

## 本地模型（turbofieldfare）兜底与隐私路由

⚠️ **仅支持 macOS（Apple Silicon）**。turbofieldfare 这套本地推理引擎是基于苹果 MLX 框架编译的，Windows / Linux 完全跑不了，这不是不死鸟的限制，是这个技术方案本身的平台限制。**不死鸟安装包本身不包含、也不会帮你安装本地模型**——这是你自己另外配置的东西，装完不死鸟不代表自动有本地模型可用。Windows / Linux 用户不会看到下面这条隐私提醒（不死鸟已经按平台自动判断，不会给你推荐一个装不上的功能）。

不死鸟 V7.5 起支持把本地 26B 模型（turbofieldfare/gemma-4-26b-a4b-it）接入两条路径，两条路径完全独立，互不影响：

### 路径一：隐私事后提醒（不是自动拦截）

**诚实说明这条路径的真实边界**：不死鸟检测到你这一轮消息可能包含敏感信息（手机号/身份证号/密码/银行卡号等）时，**这一轮内容已经发给云端模型处理完了**——技术上做不到"发送前拦截并改道"（Hermes 插件系统没有开放这个能力）。不死鸟能做的是：在这一轮的回复后面追加一段提醒，告诉你从下一轮起可以手动切到本地模型。

命中敏感词且当前不在 turbofieldfare 上时，你会在回复末尾看到：

```
检测到本轮内容可能涉及敏感/隐私信息。

如果需要用本地模型处理（数据不出网），请手动运行：
  /model turbofieldfare

注意：这次切换是手动的，不会自动切回云端——等你需要用到云端模型的能力时
（比如更强的推理），同样需要自己运行 /model <你的云端模型名> 切换回去，
不死鸟不会替你自动切回。
```

同一个会话只提醒一次（不会每轮都刷屏），已经手动切到 turbofieldfare 之后也不会再提醒。

### 路径二：欠费兜底升级（Hermes 原生机制，纯配置）

`~/.hermes/config.yaml` 的 `fallback_model` 链本地那一档已经从 3B（qwen2.5-3b-instruct-4bit）升级成 26B（turbofieldfare/gemma-4-26b-a4b-it）——主力模型欠费/失败时，Hermes 自己的原生降级机制（`try_activate_fallback()`）会按这个链条自动尝试，不需要用户操心切换，也不需要不死鸟插手代码。用 `hermes phoenix-status` 能看到当前配置的兜底链。

### 两条路径的区别

| | 路径一：隐私提醒 | 路径二：欠费兜底 |
|---|---|---|
| 触发时机 | 检测到敏感词后 | 主力模型调用失败后 |
| 切换方式 | 手动（`/model turbofieldfare`） | 自动（Hermes 原生机制） |
| 切回方式 | 手动 | Hermes 原生自动切回 |
| 目的 | 数据不出网 | 保持可用性 |

### 共用的安全阀

无论哪条路径，只要请求目标是 turbofieldfare，不死鸟都会：
- 强制该请求非流式（`stream: False`）——真机验证过，本地服务器流式+超长上下文会断连吐半截数据，非流式至少干净报错
- 请求预估超过 3277 tokens（4096 声明上限打八折）时记一条日志提醒——这一步目前**只能提醒，不能真正拦截改道**（Hermes 插件系统没有开放"切换 provider/base_url"这个能力给插件），超长请求仍然会被发给本地模型，可能会失败
